CHANGE (sandbox_tool.py; the POSIX path is unchanged and the SYSTEM prompt is unchanged, system_sha 000c5f86b8):
 - RUN_PYTHON is on when the POSIX limits exist OR Windows Job Objects exist (new _has_job_objects(): a capability
   check, not an OS-name check).
 - cmd_run_python takes the job path (_run_python_job) where POSIX limits do not exist. Each run gets its own Job
   Object (_WinJob: all Win32 calls in one class): memory cap = RUN_MEM_MB, at most ONE process, kill on close, die on
   an unhandled crash, CPU-time backstop RUN_TIMEOUT_S + 2. The BASE python.exe is started (a venv python.exe is a
   launcher that starts a second process, which the one-process limit would block). The child's env adds TEMP/TMP
   (the run's own temp folder) and SystemRoot/ComSpec/PathExt if present; nothing else passes through.
 - Handshake: the child installs the audit hook and then waits for exactly "go" on stdin; the tool sends it only after
   AssignProcessToJobObject succeeded, then closes stdin (so the script's input() gets end-of-file at once). If the job
   cannot be created or the child cannot be put in it, the child is killed and the script is NOT run (fail closed).
   Second layer: a runner that reads anything but "go" (e.g. end-of-file) exits 126 without running the script.
 - Wall-clock deadline RUN_TIMEOUT_S: TerminateJobObject(124) -> "[exit 124] TIMED OUT ..." (same text as POSIX).
   Windows' own CPU-cap code 0xC0000044 is reported the same way.
 - No per-file size limit exists in a job, so the job's total bytes written (files + output, from its IO accounting)
   are capped at RUN_MAX_WRITE_MB = 2 x RUN_MAX_FILE_MB = 40 MB -> TerminateJobObject(125), "[exit 1] (output
   reached the 40MB limit ...)". The POSIX path keeps its 20 MB per-file limit.
 - The job's memory cap makes allocation fail (MemoryError) instead of killing; when the run failed and the job's peak
   memory reached the cap, the result reads "[exit 137] KILLED: the script used more than N MB" like the POSIX
   watchdog. A MemoryError well below the cap stays the script's own error.
 - Windows crash statuses (>= 0xC0000000) are named in the result.
 - Runner (_RUNNER): resource/_posixsubprocess imported only where they exist; on Windows _winapi.CreateProcess is
   replaced (the job blocks it anyway); paths compared with normcase (Windows ignores case); '..' found with both
   separators; os.devnull allowed; os.startfile, _winapi.CreateProcess / OpenProcess / TerminateProcess /
   CreateNamedPipe, os.add_dll_directory and every winreg event are blocked; _winapi.CreateFile must stay in the
   sandbox. All of these are no-ops on Linux (proven: the Linux suite is unchanged).
